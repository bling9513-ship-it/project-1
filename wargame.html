검색어가 그대로 쿼리 문자열이 된 재고 조회

상품 재고 조회 API는 검색어를 SQL 문자열에 이어 붙여 실행합니다.

Python · inventory.py옆으로 넘겨 보기
@app.get("/stock")
      def stock():
          q = request.args.get("q", "")
          sql = "SELECT name, stock FROM items WHERE name LIKE '%" + q + "%'"
          return db.execute(sql).fetchall()

이 코드에서 가장 먼저 고쳐야 할 취약점은?

힌트
    해설 · 공격 원리와 대응

    공격 원리

    LIKE '%...%' 안에 `' OR 1=1--` 같은 값이 들어가면 문자열 리터럴이 닫히고 조건이 새로 붙습니다. 쿼리와 데이터가 하나의 문자열로 합쳐지기 때문에 DB는 입력을 '값'이 아니라 'SQL 문법'으로 해석합니다.

    실무 영향

    인증 우회, 전 테이블 덤프, UNION 기반 정보 유출, DB 권한에 따라 파일 읽기·쓰기까지 이어집니다. 쿼리를 먼저 고정하고 입력을 바인딩하면 입력은 항상 값으로만 취급됩니다.

    Vulnerable Code
    sql = "SELECT name, stock FROM items WHERE name LIKE '%" + q + "%'"
      db.execute(sql)
    Secure Code
    sql = "SELECT name, stock FROM items WHERE name LIKE ?"
      db.execute(sql, ("%" + q + "%",))

    비밀번호를 몰라도 통과하는 로그인

    로그인 API는 이메일과 비밀번호를 아래 쿼리에 그대로 이어 붙입니다. 비밀번호는 모르지만 첫 번째 계정으로 로그인해 볼 수 있습니다.

    SQL · 실제로 실행되는 쿼리옆으로 넘겨 보기
    SELECT id, role FROM users
      WHERE email = '<이메일 입력>' AND password = '<비밀번호 입력>';

    이메일 입력창에 넣을 페이로드를 완성하세요. 앞의 문자열을 닫고, 조건을 항상 참으로 만든 뒤, 뒤쪽 비밀번호 조건을 주석으로 지웁니다.

      해설 · 공격 원리와 대응

      공격 원리

      `'`로 email 문자열을 닫고 `OR 1=1`로 조건을 항상 참으로 만든 뒤 `--`로 뒤의 `AND password = ...`를 주석 처리하면, DB는 조건에 맞는 첫 번째 행을 반환합니다. 비밀번호 비교는 아예 실행되지 않습니다.

      실무 영향

            alg를 none으로 바꾼 관리자 토큰

            API 게이트웨이가 JWT 헤더의 alg 값을 그대로 사용해 검증합니다. 아래 토큰은 서명이 비어 있는데도 통과했습니다.

            디코딩된 토큰옆으로 넘겨 보기
            header    = {"alg": "none", "typ": "JWT"}
      payload   = {"sub": "user1", "role": "admin", "exp": 1799999999}
      signature = ""      # 비어 있음
            Python · auth.py옆으로 넘겨 보기
            header = jwt.get_unverified_header(token)
      alg = header["alg"]

            이 토큰이 통과할 수 있는 이유로 가장 정확한 것은?

            힌트
              해설 · 공격 원리와 대응

              공격 원리

              JWT는 헤더에 서명 알고리즘을 담습니다. 서버가 그 값을 신뢰하면 공격자가 alg를 none으로 바꾸고 서명을 비우는 것만으로 통과합니다. RS256 공개키를 HS256 비밀키로 오인하는 알고리즘 혼동(RS→HS)도 같은 뿌리입니다.

              실무 영향

              role을 admin으로 바꾼 토큰을 스스로 만들어 관리자 권한을 얻습니다. 허용 알고리즘을 서버에 고정하고, alg: none을 거부하고, kid·jku를 외부 입력으로 신뢰하지 않아야 합니다. 세션 무효화를 위해 jti와 짧은 exp도 함께 씁니다.

              Vulnerable Code
              alg = jwt.get_unverified_header(token)["alg"]
      claims = jwt.decode(token, KEY, algorithms=[alg])
              Secure Code
              claims = jwt.decode(token, PUBLIC_KEY,
                          algorithms=["RS256"],
                          options={"require": ["exp", "sub"]})

                                        $proxy_add_x_forwarded_for는 기존 헤더 뒤에 클라이언트 IP를 덧붙입니다. 클라이언트가 X-Forwarded-For: 127.0.0.1을 보내면 그 값이 앞부분에 남고, 애플리케이션이 첫 값이나 startswith로 판단하면 위조가 통과합니다. 직전 프록시에서 헤더를 덮어쓰고 신뢰 경계 기준으로 실제 접속 IP를 판단해야 합니다.

                                        실무 영향

                                        IP 기반 접근 제어가 우회되어 관리자 기능이 노출됩니다. 접근 제어는 애플리케이션이 아니라 네트워크·프록시 계층에서 하고, 감사 로그에는 신뢰한 IP를 남깁니다.

                                        Vulnerable Code
                                        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
      if request.headers.get("X-Forwarded-For", "").startswith("127."): allow()
                                        Secure Code
                                        proxy_set_header X-Forwarded-For $remote_addr;   # 클라이언트 값 무시
      ip = request.access_route[-1]                    # 신뢰 프록시 기준 실제 IP
      if ip in ADMIN_ALLOWLIST: allow()

                                          공격 원리

                                          verify=False는 인증서 체인·호스트명·만료 검증을 모두 끕니다. HTTPS라는 이름은 남지만 상대가 진짜 그 서버인지 확인하지 않으므로 같은 네트워크의 공격자가 프록시를 세워 요청과 응답을 읽고 바꿀 수 있습니다. 사내 CA를 쓰더라도 검증을 끄는 대신 CA 번들을 지정해야 합니다.

                                          실무 영향

                                          결제 금액·계좌·개인정보 변조와 세션 탈취입니다. CA 번들로 검증을 유지하고 인증서 피닝과 TLS 최소 버전 1.2 이상을 함께 적용합니다.
