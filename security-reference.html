자산·네트워크 · 01

승인 자산 인벤토리 점검

승인 대장과 실제 관측 호스트를 대조해 미등록·누락 자산을 찾습니다

nmap · awk · comm 네트워크 요청
점검 목적
점검 전에 '관리한다고 승인한 목록'과 '지금 응답하는 호스트'를 같은 기준으로 맞춥니다. 미등록 장비(섀도 IT)와 대장에만 남은 유령 자산을 한 번에 드러냅니다.
검증 기준 버전
Nmap 7.94 · GNU awk 5.1.0 · GNU coreutils comm 9.1 (Ubuntu 24.04)
입력·대상
승인 자산 대장(한 줄에 IP 하나, approved-hosts.txt) + nmap -sn -oG 저장 파일(sweep.gnmap)
필요 권한
일반 사용자 (-sn 호스트 발견은 대부분 비루트) · 로컬 서브넷 ARP 스캔은 root
실행 영향 등급
네트워크 요청 대표 흐름에 호스트 발견 스캔이 포함되어 네트워크 요청으로 표기합니다. 스캔은 승인된 대역·시간 창에서만 실행하고, 판독 명령(sort·comm)만 쓰면 로컬 파일 읽기입니다.

대표 명령어

호스트 발견 결과 저장 네트워크 요청 
nmap -sn 192.0.2.0/28 -oG sweep.gnmap

192.0.2.0/24는 RFC 5737 문서용 대역입니다. 실제 점검에서는 승인서에 적힌 대역·시간으로 바꾸고, /28처럼 작은 범위부터 확인합니다.

관측 목록 추출 로컬 파일 읽기 
awk '/Status: Up/{print $2}' sweep.gnmap | sort > observed.txt

-oG 결과의 Host: <IP> (<이름>) 줄에서 두 번째 필드가 IP입니다. 이름 해석을 껐다면 괄호 안은 비어 있습니다.

대장과 대조(미등록) 로컬 파일 읽기 
sort approved-hosts.txt > approved-sorted.txt && comm -23 observed.txt approved-sorted.txt

comm -23은 관측에만 있는 줄(미등록), comm -13은 대장에만 있는 줄(미관측)입니다. 두 파일 모두 정렬되어 있어야 합니다.

미관측 자산 확인 로컬 파일 읽기 
comm -13 observed.txt approved-sorted.txt

응답이 없어서 빠진 것인지, 실제로 회수된 것인지 구분하려면 임대 이력·자산 관리 기록을 함께 봅니다.

대장 형식만 먼저 점검 로컬 파일 읽기 
awk 'NF!=1 || $1 !~ /^([0-9]{1,3}\.){3}[0-9]{1,3}$/' approved-hosts.txt

주석·CIDR·빈 줄이 섞이면 대조 결과가 통째로 어긋납니다. 스캔 전에 대장 형식을 먼저 정리합니다.

결과 판독

정상 출력
  • comm -23과 comm -13이 모두 비어 있으면 대장과 관측이 일치합니다.
  • 관측 IP가 모두 대장과 같은 형식(한 줄 IP)이고, -n을 썼다면 호스트 이름이 비어 있어도 정상입니다.
  • 마지막 Nmap done 줄의 hosts up 수가 범위 크기와 모순되지 않습니다.
이상 징후
  • comm -23에 IP가 나오면 미등록 장비입니다. DHCP 동적 대역이면 임대 이력과 함께 봅니다.
  • comm -13에 IP가 남으면 회수·폐기 후 정리되지 않은 유령 자산이거나 응답이 차단된 상태입니다.
  • 같은 IP가 점검마다 다른 호스트 이름으로 나타나면 IP 재할당이 잦은 대역입니다.
  • 대장에 없는 대역(예: 다른 VLAN)이 관측에 섞여 있으면 승인 범위를 넘은 스캔입니다.
오탐 주의
  • ICMP를 차단한 망에서 -sn만 쓰면 살아 있는 호스트가 빠져 '미관측'으로 보입니다.
  • 가상 IP(VIP)·로드밸런서·멀티홈 호스트는 여러 주소로 보이거나 한쪽만 응답합니다.
  • VPN·무선 클라이언트는 세션에 따라 붙었다 떨어져 오탐이 생깁니다.
  • 대장 형식이 섞여 있으면(주석·CIDR) 정상 자산도 미등록으로 나옵니다.
조치
  • 미등록 자산은 소유자·용도를 확인해 대장에 등록하거나 네트워크에서 격리합니다. 확인 전 차단은 업무 중단을 부를 수 있습니다.
  • 대장에만 있는 항목은 폐기·회수 이력을 확인해 정리하고, 회수 예정이면 만료일을 적습니다.
  • 점검 주기(예: 2주)와 대장 갱신 담당을 정해 기록에 남깁니다.
재점검
  • 같은 대장·같은 범위로 다시 수집해 두 대조 결과가 모두 비는지 확인합니다.
  • 대장을 갱신했다면 갱신 커밋 해시와 점검 시각을 보고서에 남깁니다.

Nmap 결과 파일 판독

저장된 스캔 결과에서 포트 상태와 서비스, 판정 근거를 오탐 없이 읽습니다

nmap · xmlstarlet 로컬 파일 읽기
점검 목적
-oX/-oN으로 남긴 결과를 나중에 다시 읽어 열린 포트·서비스·상태 판정 근거(state reason)를 확정합니다. 스캔을 다시 돌리지 않고도 보고서를 만들 수 있게 합니다.
검증 기준 버전
Nmap 7.94 · xmlstarlet 1.6.1
입력·대상
저장 파일 scan.xml(-oX) 또는 scan.txt(-oN)
필요 권한
일반 사용자 (파일 읽기)
실행 영향 등급
로컬 파일 읽기 대표 명령 중 첫 줄(스캔 실행)만 네트워크 요청이고, 나머지 판독 명령은 저장 파일만 읽습니다. 이미 저장된 결과가 있으면 스캔 없이 판독만 하면 됩니다.

대표 명령어

결과를 두 형식으로 저장 네트워크 요청 
nmap -sT -sV --top-ports 100 -oX scan.xml -oN scan.txt 192.0.2.10

-sT는 root 없이 동작하는 connect 스캔입니다. XML은 자동화, 일반 텍스트는 사람이 읽기 좋습니다.

열린 포트만 뽑기 로컬 파일 읽기 
xmlstarlet sel -t -m "//port[state/@state='open']" -v "ancestor::host/address[@addrtype='ipv4']/@addr" -o " " -v "@portid" -o "/" -v "service/@name" -n scan.xml

주소·포트·서비스 이름을 한 줄로 정리합니다. IP가 여러 개인 호스트는 ipv4 주소만 골라 중복을 피합니다.

호스트 상태 확인 로컬 파일 읽기 
xmlstarlet sel -t -m "//host" -v "address[@addrtype='ipv4']/@addr" -o " " -v "status/@state" -n scan.xml

up/down과 판정 이유를 봅니다. -Pn으로 스캔하면 응답이 없어도 up으로 기록됩니다.

상태와 판정 근거 로컬 파일 읽기 
xmlstarlet sel -t -m "//port" -v "@portid" -o " " -v "state/@state" -o " " -v "state/@reason" -n scan.xml

syn-ack(열림), reset(닫힘), no-response(filtered)를 구분합니다. filtered를 닫힘으로 보고하면 정책 검토가 어긋납니다.

일반 텍스트에서 열린 줄만 로컬 파일 읽기 
grep -E '^[0-9]+/(tcp|udp)[[:space:]]+open' scan.txt

open|filtered는 이 패턴에 걸리지 않습니다. 포함하려면 open 대신 open| 로 넓혀 셉니다.

옵션별 영향 해부

옵션의미부하·네트워크 / 파일 쓰기 / 민감정보 영향
-sTTCP connect 스캔root 불필요. 대상 애플리케이션 로그에 연결 기록이 남습니다.
-sSTCP SYN(half-open) 스캔root 필요. 애플리케이션 로그에는 덜 남지만 IPS 탐지가 쉽습니다.
-sV서비스·버전 확인배너·프로브 요청으로 부하가 늘고, 프록시 환경에서 오탐이 생깁니다.
--reason상태 판정 근거 표시출력이 길어지지만 filtered와 closed 구분에 필요합니다.
-Pn호스트 발견 생략ICMP 차단 대상도 스캔합니다. 무응답 대역에서는 시간이 크게 늘어납니다.
--open열린 포트만 표시filtered가 사라져 방화벽 뒤 상태를 놓칠 수 있습니다.
-oX / -oNXML / 일반 텍스트 저장파일 쓰기. 이후 판독은 읽기만 합니다.
--top-ports 100상위 100개 포트만범위가 줄지만 실제 서비스 포트를 놓칠 수 있습니다.

결과 판독

정상 출력
  • <status state="up"/>와 상태 근거 reason="syn-ack"가 함께 있습니다.
  • 예상한 포트만 open, 나머지는 closed(reset) 또는 filtered(no-response)입니다.
  • 서비스 이름이 역할과 맞습니다(443 → https, 22 → ssh).
이상 징후
  • 22·3389·5900·9200·6379 같은 관리 포트가 예상 밖 대역에서 open입니다.
  • open|filtered가 대량입니다. UDP 스캔에서 흔하며 열림으로 단정하면 안 됩니다.
  • 서비스 배너와 포트가 불일치합니다(80 → ssh). 터널링·포트 포워딩을 의심합니다.
  • reason="admin-prohibited"는 중간 장비가 명시적으로 차단했다는 뜻입니다.
오탐 주의
  • -Pn 없이 ICMP가 차단되면 'Host seems down'으로 보입니다.
  • 로드밸런서·프록시가 모든 포트에 같은 배너를 주면 버전이 오탐됩니다.
  • tcpwrappers·rate limit으로 일부 포트가 간헐적으로 filtered로 보입니다.
  • 스캔 도중 서비스가 재시작되면 state가 섞여 기록됩니다.
조치
  • 불필요 포트는 서비스를 중지하고 방화벽 정책으로 닫습니다. 필요한 포트만 승인 목록에 남깁니다.
  • 배너·버전 노출을 줄이고, 관리 포트는 점프 호스트·VPN 뒤로 옮깁니다.
  • filtered가 의도된 정책인지 네트워크 담당과 확인합니다.
재점검
  • 같은 옵션으로 재스캔해 열린 포트 집합을 comm으로 비교하고 차이만 검토합니다.
  • 보고서에 스캔 시각·옵션·대상 대역을 함께 남겨 재현 가능하게 합니다.

샘플 증적 (마스킹)

8080은 응답이 없어 filtered입니다. 닫힘으로 보고하면 방화벽 정책 검토가 어긋납니다.

웹·API · 03

보안 응답 헤더·CORS 확인

CSP·HSTS·프레임 차단과 CORS 허용 출처를 응답 머리말로 확인합니다

curl 네트워크 요청
점검 목적
인가된 테스트 대상이 브라우저에 어떤 보안 정책을 내려 주는지 확인합니다. CSP·HSTS·프레임 차단·콘텐츠 타입 추측 차단과 CORS 허용 출처를 응답 헤더만으로 판정합니다.
검증 기준 버전
curl 8.5.0 (x86_64-pc-linux-gnu)
입력·대상
로컬 테스트 서버 http://127.0.0.1:8080 (테스트 도메인 표기는 fixture.test)
필요 권한
일반 사용자
실행 영향 등급
네트워크 요청 대상 서버로 요청을 보냅니다. 인가된 테스트 대상·경로에 필요한 최소 횟수만 보내고, 운영 환경에는 변경 관리 창에서 실행합니다.

대표 명령어

응답 헤더만 받기 네트워크 요청 
curl -sS -D - -o /dev/null http://127.0.0.1:8080/

본문은 버리고 헤더만 stdout으로 받습니다. 리다이렉트 뒤 최종 응답을 봐야 하면 -L을 붙입니다.

보안 헤더만 추리기 네트워크 요청 
curl -sSI http://127.0.0.1:8080/ | grep -iE '^(content-security-policy|strict-transport-security|x-frame-options|x-content-type-options|referrer-policy)'

HEAD를 지원하지 않는 서버는 405를 줍니다. 그때는 -sS -D - -o /dev/null로 GET 헤더를 봅니다.

CORS 사전 요청 재현 네트워크 요청 
curl -sS -i -X OPTIONS -H 'Origin: https://fixture.test' -H 'Access-Control-Request-Method: GET' http://127.0.0.1:8080/api/items

브라우저가 보내는 preflight를 그대로 흉내 냅니다. 응답의 Access-Control-Allow-Origin이 요청 Origin과 일치하는지 봅니다.

허용 목록 밖 출처로 한 번 네트워크 요청 
curl -sS -D - -o /dev/null -H 'Origin: https://untrusted.test' http://127.0.0.1:8080/api/items

ACAO가 비어 있거나 허용 출처만 나오면 정상입니다. 요청 Origin을 그대로 반사하면 위험합니다.

상태 코드·응답 시간 함께 네트워크 요청 
curl -sS -I --max-time 5 -w '\n%{http_code} %{time_total}s\n' http://127.0.0.1:8080/

여러 경로를 돌 때 결과를 표로 정리하기 좋습니다.

옵션별 영향 해부

옵션의미부하·네트워크 / 파일 쓰기 / 민감정보 영향
-I / --headHEAD 요청일부 서버는 405로 거절합니다. 그때는 GET 헤더를 봅니다.
-D -응답 헤더를 stdout으로본문과 섞이지 않게 -o /dev/null과 함께 씁니다.
-o /dev/null본문 폐기큰 응답을 받아도 저장하지 않습니다.
-L리다이렉트 추적최종 응답 기준으로 판정합니다. --max-redirs로 상한을 둡니다.
-k인증서 검증 생략판정을 흐리므로 진단 목적 외에는 쓰지 않습니다.
-H요청 헤더 추가Origin·Access-Control-Request-* 로 CORS 사전 요청을 재현합니다.
--max-time전체 시간 상한느린 대상에서 점검이 멈추지 않게 합니다.
-w출력 형식 지정상태 코드·응답 시간을 결과에 함께 남깁니다.

결과 판독

정상 출력
  • content-security-policy에 default-src 'self', object-src 'none', frame-ancestors가 있고 unsafe-inline·unsafe-eval이 없습니다.
  • strict-transport-security: max-age=31536000; includeSubDomains가 HTTPS 응답에 있습니다.
  • x-frame-options: DENY(또는 SAMEORIGIN), x-content-type-options: nosniff, referrer-policy가 지정되어 있습니다.
  • CORS는 허용 출처가 정확히 나열되고, 자격증명을 쓰는 경로에 *가 없습니다.
이상 징후
  • 보안 헤더가 하나도 없고 server·x-powered-by만 노출됩니다.
  • x-frame-options: ALLOW-FROM ...(폐기된 값)이거나 frame-ancestors가 없습니다.
  • access-control-allow-origin: *와 access-control-allow-credentials: true가 함께 있습니다.
  • access-control-allow-origin: null이거나 요청 Origin을 그대로 반사합니다.
  • HSTS가 HTTP 응답에만 있고 HTTPS 응답에는 없습니다.
오탐 주의
  • CDN·리버스 프록시가 헤더를 덧붙이거나 지웁니다. 원본과 CDN 응답을 구분해 봅니다.
  • HEAD가 405라 헤더가 없는 것처럼 보입니다. GET으로 다시 확인합니다.
  • 301/302만 보고 판정하면 최종 페이지 정책을 놓칩니다(-L).
  • HTTP로 테스트해 HSTS가 없다고 결론 내리면 안 됩니다. HSTS는 HTTPS 응답에서만 의미가 있습니다.
조치
  • CSP는 Content-Security-Policy-Report-Only로 먼저 적용해 위반 로그를 모은 뒤 enforce로 전환합니다.
  • HSTS는 includeSubDomains·preload의 되돌리기 어려운 영향을 확인하고 max-age를 단계적으로 올립니다.
  • CORS는 허용 출처를 화이트리스트로 고정하고, 자격증명이 필요한 경로에는 *를 쓰지 않습니다.
재점검
  • 같은 명령으로 다시 수집해 헤더 집합을 이전 결과와 비교합니다.
  • 브라우저 개발자 도구 콘솔에서 CSP 위반이 0인지 확인합니다.

샘플 증적 (마스킹)

첫 블록은 문서 응답, 둘째는 허용 출처에서 보낸 API 응답입니다. ACAO가 요청 Origin과 정확히 일치하고 vary: Origin이 함께 있어야 캐시 오염을 막습니다.

웹·API · 04

HTTP 메서드·인증 응답 코드

허용 메서드와 인증 필요 여부를 상태 코드로 확인합니다

curl 네트워크 요청
점검 목적
엔드포인트가 어떤 메서드를 받아 주고, 인증 없이 어떤 응답을 주는지 확인합니다. 인증 없이 200이 나오는 경로가 가장 먼저 볼 신호입니다.
검증 기준 버전
curl 8.5.0
입력·대상
로컬 테스트 서버 http://127.0.0.1:8080/api/items · http://127.0.0.1:8080/admin
필요 권한
일반 사용자
실행 영향 등급
네트워크 요청 대상 서버로 요청을 보냅니다. 무효 토큰 1회, 메서드별 1회처럼 최소 횟수만 보내고 반복 시도·대입은 하지 않습니다.

대표 명령어

토큰 없이 한 번 네트워크 요청 
curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/api/items

401/403이면 인증 게이트가 살아 있습니다. 200이면 본문까지 확인해 실제 데이터인지 봅니다.

허용 메서드 확인 네트워크 요청 
curl -sS -i -X OPTIONS http://127.0.0.1:8080/api/items | grep -iE '^(allow|access-control-allow-methods)'

Allow 헤더에 실제 지원 메서드가 나옵니다. PUT·DELETE·TRACE가 포함되어 있으면 용도를 확인합니다.

TRACE 거절 확인 네트워크 요청 
curl -sS -o /dev/null -w '%{http_code}\n' -X TRACE http://127.0.0.1:8080/api/items

TRACE는 405/501이 정상입니다. 200이면 Cross-Site Tracing 위험을 검토합니다.

무효 토큰으로 구분 확인 네트워크 요청 
curl -sS -o /dev/null -w '%{http_code}\n' -H 'Authorization: Bearer invalid-token' http://127.0.0.1:8080/api/items

401(인증 실패)과 403(권한 부족)의 구분을 확인합니다. 무효 토큰은 한 번만 사용합니다.

관리 경로 응답 네트워크 요청 
curl -sS -o /dev/null -w '%{http_code} %{redirect_url}\n' http://127.0.0.1:8080/admin

302(로그인 이동)나 403이 정상입니다. 200으로 관리 화면이 나오면 인증 누락을 의심합니다.

옵션별 영향 해부

옵션의미부하·네트워크 / 파일 쓰기 / 민감정보 영향
-X메서드 지정서버가 받지 않는 메서드에도 요청을 보냅니다. 405 확인용입니다.
-w '%{http_code}'상태 코드 출력본문 없이 결과만 비교합니다.
-o /dev/null본문 폐기대용량·바이너리 응답을 안전하게 버립니다.
-H 'Authorization: ...'인증 헤더 주입무효 토큰 1회. 실제 자격증명은 넣지 않습니다.
--max-time시간 상한응답이 멈춘 대상에서 점검이 끝나지 않는 일을 막습니다.
-b / -c쿠키 전송·저장로그인 후 인증 필요 경로로 이어지는 흐름을 재현합니다.
--path-as-is경로 정규화 금지경로 우회 점검에만 사용합니다. 일반 점검에서는 쓰지 않습니다.

결과 판독

정상 출력
  • 토큰 없음 401, 무효 토큰 401, 권한 없는 유효 토큰 403으로 구분됩니다.
  • Allow: GET, POST, OPTIONS처럼 실제 지원 메서드만 나열되고 TRACE는 405입니다.
  • 관리 경로는 302(로그인) 또는 403입니다.
이상 징후
  • 토큰 없이 /api/...가 200과 데이터를 반환합니다.
  • TRACE가 200이거나 Allow에 PUT·DELETE·TRACE가 포함됩니다.
  • 500과 함께 스택 트레이스·SQL 오류 문구가 노출됩니다.
  • 302 대신 200으로 관리 화면 HTML을 반환합니다.
  • X-HTTP-Method-Override: DELETE가 동작합니다.
오탐 주의
  • SPA가 모든 경로에 200 + index.html을 반환합니다. 본문이 비어 있는지 확인합니다.
  • API 게이트웨이가 401 대신 302/HTML 로그인 페이지를 돌려줍니다.
  • CDN 캐시가 이전 200 응답을 재생합니다.
  • WAF가 403을 반환해 애플리케이션 인증 실패와 구분되지 않습니다(응답 헤더·본문으로 구분).
조치
  • 인증 미들웨어를 라우터 단위로 강제하고, 화이트리스트(로그인·헬스체크)만 예외로 둡니다.
  • 메서드는 필요한 것만 허용하고 TRACE·불필요 확장 메서드를 비활성화합니다.
  • 오류 응답에서 스택·내부 경로를 제거합니다.
재점검
  • 같은 경로·같은 메서드로 재확인해 상태 코드 표를 이전 결과와 비교합니다.
  • 자동 테스트에 401/403 기대값을 넣어 회귀를 막습니다.

인증 없는 요청과 무효 토큰이 모두 401이고 TRACE가 405이면 게이트가 정상 동작합니다.

암호화와 이름 해석이 기대대로 동작하는지 봅니다. 인증서 파일과 로컬 리졸버만 사용합니다.

TLS·DNS · 05

인증서·체인·유효기간 판독

주체·발급자·만료일·SAN·체인·협상 프로토콜을 확인합니다

openssl 네트워크 요청
점검 목적
저장된 인증서 파일과 테스트 서버 핸드셰이크로 만료일·SAN·체인·키 길이·협상 프로토콜을 확인합니다. 만료·호스트명 불일치·약한 알고리즘은 브라우저에서 곧바로 차단으로 이어집니다.
검증 기준 버전
OpenSSL 3.0.13 (Ubuntu 24.04)
입력·대상
로컬 인증서 fixture.crt·fixture-ca.crt / 테스트 서버 127.0.0.1:8443(SNI fixture.test)
필요 권한
일반 사용자
실행 영향 등급
네트워크 요청 파일 판독 명령은 로컬 파일만 읽고, s_client 명령만 테스트 서버와 핸드셰이크합니다. 운영 서버에는 변경 관리 창에서 확인합니다.

대표 명령어

주체·발급자·기간 로컬 파일 읽기 
openssl x509 -in fixture.crt -noout -subject -issuer -dates -serial

개인키는 다루지 않고 공개 인증서만 읽습니다.

SAN·키 길이·서명 로컬 파일 읽기 
openssl x509 -in fixture.crt -noout -text | grep -A1 -E 'Subject Alternative Name|Public-Key|Signature Algorithm'

최신 브라우저는 CN을 무시하고 SAN으로 이름을 검증합니다. SAN에 실제 접속 이름이 있어야 합니다.

로컬 체인 검증 로컬 파일 읽기 
openssl verify -CAfile fixture-ca.crt -untrusted fixture-chain.crt fixture.crt

중간 CA가 있으면 -untrusted로 넘깁니다. 체인 순서가 틀리면 여기서 실패합니다.

서버가 보낸 인증서 읽기 네트워크 요청 
openssl s_client -connect 127.0.0.1:8443 -servername fixture.test -showcerts </dev/null 2>/dev/null | openssl x509 -noout -subject -dates

-servername(SNI)을 빼면 서버 기본 인증서가 와서 다른 결과를 볼 수 있습니다.

만료 임박 확인 네트워크 요청 
openssl s_client -connect 127.0.0.1:8443 -servername fixture.test -checkend 2592000 </dev/null

30일(2592000초) 안에 만료되면 경고를 출력합니다. 배포 전 검사에 그대로 넣을 수 있습니다.

협상 프로토콜 고정 네트워크 요청 
openssl s_client -connect 127.0.0.1:8443 -tls1_2 </dev/null 2>&1 | grep -E 'Protocol|Cipher'

TLS 1.2로 붙는지 확인합니다. 서버가 거절하면 handshake failure가 납니다.

옵션별 영향 해부

옵션의미부하·네트워크 / 파일 쓰기 / 민감정보 영향
-in / -noout파일 읽기 / 요약만 출력공개 인증서 파일만 읽습니다.
-text인증서 전체 디코드SAN·확장·키 길이까지 보입니다. 출력이 깁니다.
-servernameSNI 지정가상 호스트 서버에서 필수입니다. 없으면 기본 인증서를 읽습니다.
-showcerts서버가 보낸 체인 전체 출력중간 CA 누락을 판별합니다.
-CAfile / -untrusted신뢰 루트 / 중간 CA 지정로컬 검증으로 시스템 번들 차이를 배제합니다.
-checkend NN초 내 만료 확인종료 코드로 자동화할 수 있습니다.
-tls1_2 / -tls1_3특정 프로토콜로 협상하위 버전 허용 여부를 확인합니다.
-brief한 줄 요약프로토콜·암호·검증 결과만 볼 때 편합니다.

결과 판독

정상 출력
  • subject=CN = fixture.test이고 SAN에 실제 접속 이름이 포함되어 있습니다.
  • notAfter까지 90일 이상 남고, 발급자가 신뢰 체인에 연결됩니다.
  • RSA 2048비트 이상 또는 EC P-256, 서명 SHA-256 이상입니다.
  • Protocol: TLSv1.3(또는 TLSv1.2)과 Verify return code: 0 (ok)가 함께 나옵니다.
이상 징후
  • notAfter가 지났거나 30일 이내입니다.
  • verify error:num=10:certificate has expired 또는 num=62:hostname mismatch입니다.
  • 체인에 중간 CA가 없어 unable to get local issuer certificate가 납니다.
  • RSA 1024·SHA-1·TLSv1.0/1.1 협상이 성공합니다.
  • SAN 없이 CN만 있는 인증서입니다(최신 브라우저는 CN을 무시).
오탐 주의
  • SNI 없이 접속해 기본 인증서를 읽고 불일치로 오판합니다.
  • 로컬 PC 시계 오차로 유효기간 오류가 납니다.
  • 시스템 CA 번들에 사내 루트가 없어 검증에 실패합니다(인증서 자체는 정상).
  • -showcerts 출력의 첫 인증서가 서버 인증서가 아닌 체인 순서 문제일 수 있습니다.
조치
  • 만료 30일 전 알림과 자동 갱신(ACME)으로 교체합니다.
  • 서버가 체인 전체(중간 CA 포함)를 보내도록 설정합니다.
  • TLS 1.0/1.1과 약한 암호 스위트를 비활성화하고 HSTS와 함께 적용합니다.
재점검
  • -checkend를 배포 파이프라인에 넣어 만료 임박을 자동으로 잡습니다.
  • 갱신 후 s_client로 체인·만료·프로토콜을 다시 확인합니다.

샘플 증적 (마스킹)

발급자·기간·프로토콜·검증 결과가 한 번에 확인됩니다. 실제 인증서 값은 마스킹해 보고서에 옮깁니다.

TLS·DNS · 06

TXT·SPF·DMARC 레코드 확인

메일 발신 정책과 인증서 발급 허용 범위를 레코드로 확인합니다

dig 네트워크 요청
점검 목적
도메인의 TXT 계열 레코드를 읽어 메일 발신 정책(SPF·DMARC)과 인증서 발급 허용(CAA)이 의도대로 설정됐는지 확인합니다.
검증 기준 버전
BIND 9.18.24 dig
입력·대상
로컬 리졸버 127.0.0.1 · 테스트 존 fixture.test
필요 권한
일반 사용자
실행 영향 등급
네트워크 요청 리졸버에 질의합니다. @127.0.0.1처럼 질의 서버를 고정하면 외부 유출과 캐시 차이를 줄일 수 있습니다.

대표 명령어

SPF(TXT) 확인 네트워크 요청 
dig @127.0.0.1 fixture.test TXT +short

질의 서버를 지정하면 어떤 리졸버가 응답했는지 분명해집니다.

MX 확인 네트워크 요청 
dig @127.0.0.1 fixture.test MX +short

메일을 받는 서버가 실제 운영 서버인지 확인합니다.

DMARC 확인 네트워크 요청 
dig @127.0.0.1 _dmarc.fixture.test TXT +short

DMARC는 루트가 아니라 _dmarc. 하위 이름에 있습니다.

CAA 확인 네트워크 요청 
dig @127.0.0.1 fixture.test CAA +short

인증서를 발급받을 수 있는 CA를 제한합니다. 값이 없으면 제한이 없는 상태입니다.

응답 상태까지 보기 네트워크 요청 
dig @127.0.0.1 fixture.test TXT +noall +answer +comments | head -20

status: NXDOMAIN이면 이름 자체가 없고, NOERROR에 answer가 비면 레코드가 없는 것입니다.

DNSSEC·분할 TXT 네트워크 요청 
dig @127.0.0.1 fixture.test TXT +dnssec +multi

긴 TXT는 255자 단위로 나뉩니다. +multi로 한 줄에 하나씩 읽습니다.

옵션별 영향 해부

옵션의미부하·네트워크 / 파일 쓰기 / 민감정보 영향
@server질의 서버 지정로컬 리졸버로 외부 유출과 캐시 차이를 줄입니다.
+short답만 간단히값 비교에 편하지만 TTL·플래그는 사라집니다.
+noall +answeranswer 섹션만스크립트 파싱에 안정적입니다.
+dnssecDNSSEC 레코드 요청서명과 ad 플래그를 확인합니다.
+multi한 줄에 한 레코드255자로 분할된 TXT를 읽기 좋습니다.
+trace루트부터 반복 질의외부 질의가 많아집니다. 정책 확인용으로만 씁니다.
-x역방향 조회PTR 레코드를 확인합니다.
+tcpTCP로 질의응답이 잘렸을 때(TC 플래그) 다시 받습니다.

결과 판독

정상 출력
  • SPF가 v=spf1 include:mail.fixture.test -all처럼 단일 레코드이고 -all로 끝납니다.
  • DMARC가 v=DMARC1; p=quarantine; rua=mailto:dmarc@fixture.test처럼 정책과 보고 주소를 가집니다.
  • CAA가 0 issue "fixture-ca.test"로 발급 CA를 제한합니다.
  • 응답이 status: NOERROR에 flags: qr rd ra입니다.
이상 징후
  • SPF 레코드가 2개 이상이거나 +all(모두 허용)입니다.
  • include 중첩으로 SPF lookup 10회를 넘어 permerror가 납니다.
  • DMARC가 p=none으로 장기 방치돼 있거나 rua 주소가 없습니다.
  • _dmarc가 NXDOMAIN이라 DMARC가 아예 없습니다.
  • CAA에 0 issue ";"(전체 금지)나 의도하지 않은 CA가 있습니다.
  • TXT에 내부 호스트명·토큰 흔적이 남아 있습니다.
오탐 주의
  • 255자로 분할된 TXT를 하나의 레코드로 오해합니다.
  • CNAME 뒤에 TXT가 있어 첫 질의에서 비어 보입니다.
  • TTL 캐시 때문에 방금 바꾼 값이 보이지 않습니다(권한 서버에 직접 질의).
  • DNSSEC 검증 실패는 리졸버 설정 문제일 수 있습니다.
조치
  • SPF는 단일 레코드로 정리하고 include 수를 줄입니다.
  • DMARC는 p=none으로 로그를 모은 뒤 quarantine, reject로 단계적으로 올립니다.
  • CAA는 실제 사용하는 CA만 남깁니다.
재점검
  • TTL이 지난 뒤 같은 질의를 다시 실행해 값이 반영됐는지 확인합니다.
  • 메일 발신 테스트로 Authentication-Results 헤더의 spf·dkim·dmarc 결과를 확인합니다.

샘플 증적 (마스킹)

SPF·DMARC·CAA가 모두 한 줄로 확인됩니다. 따옴표는 255자 단위로 나뉜 TXT 문자열의 경계입니다.

이미 저장된 캡처를 다시 뜨지 않고 필터로 좁혀 통신 대상과 실패 원인을 읽습니다.

패킷 · 07

PCAP 필터링과 핸드셰이크 판독

저장된 캡처에서 HTTP·DNS·TLS 핸드셰이크만 골라 읽습니다

tshark 로컬 파일 읽기
점검 목적
이미 저장된 캡처(sample.pcap)를 다시 뜨지 않고 필터로 좁혀 통신 대상과 실패 원인을 확인합니다. 실시간 캡처 권한 없이도 분석할 수 있는 것이 장점입니다.
검증 기준 버전
Tshark 4.2.2 (Wireshark 4.2.2)
입력·대상
저장된 캡처 sample.pcap
필요 권한
일반 사용자(파일 읽기) · 라이브 캡처는 root 또는 캡처 권한
실행 영향 등급
로컬 파일 읽기 -r로 저장 파일만 읽습니다. 라이브 캡처(-i)와 파일 쓰기(-w)는 별도 승인이 필요합니다.

대표 명령어

무엇이 들었는지 요약 로컬 파일 읽기 
tshark -r sample.pcap -q -z io,phs

프로토콜 계층 통계로 어떤 트래픽이 있는지 먼저 파악합니다.

HTTP 요청 추출 로컬 파일 읽기 
tshark -r sample.pcap -Y 'http.request' -T fields -e frame.number -e ip.dst -e http.host -e http.request.method -e http.request.uri

평문 HTTP만 잡힙니다. 본문 덤프(-x, -A)는 민감정보가 있으니 필요한 경우에만 씁니다.

DNS 실패만 로컬 파일 읽기 
tshark -r sample.pcap -Y 'dns.flags.rcode != 0' -T fields -e frame.number -e dns.qry.name -e dns.flags.rcode

rcode 3은 NXDOMAIN, 2는 SERVFAIL입니다. 반복 NXDOMAIN은 오타·DGA·차단을 구분해 봅니다.

TLS SNI 확인 로컬 파일 읽기 
tshark -r sample.pcap -Y 'tls.handshake.type == 1 || tls.handshake.type == 2' -T fields -e frame.number -e tls.handshake.extensions_server_name -e tls.handshake.type

type 1은 Client Hello, 2는 Server Hello입니다. SNI로 실제 접속한 이름을 확인합니다.

전문가 정보만 로컬 파일 읽기 
tshark -r sample.pcap -Y 'tcp.analysis.flags' -T fields -e frame.number -e _ws.expert.message

재전송·순서 뒤바뀜·0 window 같은 신호만 모읍니다.

TLS 경고 로컬 파일 읽기 
tshark -r sample.pcap -Y 'tls.alert_message' -T fields -e frame.number -e tls.alert_message.desc

40(handshake_failure)·46(certificate_unknown) 등 협상 실패 원인을 봅니다.

옵션별 영향 해부

옵션의미부하·네트워크 / 파일 쓰기 / 민감정보 영향
-r파일 읽기디스크만 읽습니다. 권한이 필요 없습니다.
-Y디스플레이 필터파일 전체를 파싱한 뒤 거르므로 대용량에서 메모리·시간을 씁니다.
-T fields -e필드 단위 출력표·CSV로 가공하기 좋습니다.
-q -z io,phs통계만 출력패킷 목록 대신 요약을 봅니다.
-c NN개에서 멈춤긴 캡처의 앞부분만 볼 때 유용합니다.
-22-pass 분석TCP 재조립·지연 판정 정확도가 올라갑니다.
-x / -Ahex/ASCII 덤프자격증명·개인정보가 노출될 수 있어 마스킹이 필요합니다.
-w캡처 쓰기라이브 캡처에만 쓰며 별도 승인이 필요합니다.

결과 판독

정상 출력
  • io,phs에 TCP/UDP/TLS/DNS 계층이 균형 있게 나타납니다.
  • HTTP 요청의 Host가 기대 도메인이고 DNS rcode가 0입니다.
  • Client Hello의 SNI가 접속하려던 이름과 일치하고, Server Hello 뒤에 alert가 없습니다.
이상 징후
  • Client Hello의 SNI가 내부 호스트명·IP이거나 SNI 없이 IP로 접속합니다.
  • 평문 HTTP로 POST /login, Authorization: Basic ...이 보입니다.
  • NXDOMAIN이 반복되고 짧은 간격에 서로 다른 무작위 이름이 나옵니다(DGA 의심).
  • retransmission·zero_window·RST 폭주가 다수입니다.
  • TLS alert 40·46·48이 반복됩니다(설정 불일치).
오탐 주의
  • 캡처 시작 전에 맺어진 세션은 Client Hello가 없습니다.
  • TSO/LRO 오프로드로 캡처된 패킷 크기가 비정상이고 체크섬 오류가 표시됩니다.
  • HTTP/3(QUIC)는 UDP 443이라 http.request 필터에 잡히지 않습니다.
  • 프록시·NAT 환경에서는 SNI와 실제 목적지 IP가 다릅니다.
조치
  • 평문 자격증명이 확인되면 계정 비밀번호를 회수(rotate)하고 HTTPS를 강제합니다.
  • SNI 불일치·비정상 DNS는 프록시 정책과 단말 감염 여부를 확인합니다.
  • 반복 alert는 서버·클라이언트 암호 스위트 설정을 맞춥니다.
재점검
  • 같은 조건에서 새로 캡처해 같은 필터로 다시 확인합니다.
  • 필터별 건수를 이전 캡처와 비교해 감소를 증명합니다.

샘플 증적 (마스킹)

rcode 2는 SERVFAIL, 3은 NXDOMAIN입니다. 같은 이름이 반복되면 설정 문제, 무작위 이름이 반복되면 DGA를 의심합니다.

패킷 · 08

저장 캡처 플래그·재전송 판독

플래그와 시간 중심 한 줄 요약으로 스캔·거절·재전송을 찾습니다

tcpdump 로컬 파일 읽기
점검 목적
저장된 캡처를 한 줄 요약으로 빠르게 훑어 스캔성 SYN, RST/FIN, 재전송을 찾습니다. tshark보다 가볍고, 파일만 읽으므로 캡처 권한이 필요 없습니다.
검증 기준 버전
tcpdump 4.99.4 / libpcap 1.10.4
입력·대상
저장된 캡처 sample.pcap
필요 권한
일반 사용자(파일 읽기) · 라이브 캡처는 root
실행 영향 등급
로컬 파일 읽기 -r로 파일만 읽습니다. -i 라이브 캡처와 -w 파일 쓰기는 승인과 디스크 용량 확인이 필요합니다.

대표 명령어

앞부분 훑기 로컬 파일 읽기 
tcpdump -nn -r sample.pcap -c 20

-nn은 이름·서비스 해석을 꺼 DNS 질의 없이 빠르게 읽습니다.

날짜·시각 포함 로컬 파일 읽기 
tcpdump -nn -tttt -r sample.pcap -c 20

사건 시간대를 다른 로그와 맞출 때 씁니다.

SYN만(연결 시도) 로컬 파일 읽기 
tcpdump -nn -r sample.pcap 'tcp[tcpflags] & tcp-syn != 0 and tcp[tcpflags] & tcp-ack == 0' -c 30

SYN만 있고 ACK가 없는 패킷이 연결 시도입니다. 짧은 시간에 여러 포트로 퍼지면 스캔 신호입니다.

RST·FIN 로컬 파일 읽기 
tcpdump -nn -r sample.pcap 'tcp[tcpflags] & (tcp-rst|tcp-fin) != 0' -c 20

RST 폭주는 닫힌 포트·방화벽 거절, FIN은 정상 종료 패턴입니다.

한 흐름만 로컬 파일 읽기 
tcpdump -nn -tttt -r sample.pcap 'host 192.0.2.10 and port 443'

필요한 흐름만 떼어 시간 순으로 봅니다.

상세(TTL·길이) 로컬 파일 읽기 
tcpdump -nn -vv -r sample.pcap -c 5

TTL로 경로·OS를 추정할 수 있지만 단정하지 않습니다.

옵션별 영향 해부

옵션의미부하·네트워크 / 파일 쓰기 / 민감정보 영향
-nn주소·포트 해석 금지DNS·services 질의가 없어 빠르고 조용합니다.
-r파일 읽기디스크만 읽습니다.
-c NN패킷 후 종료대용량 파일에서 안전합니다.
-tttt날짜+시각 표시다른 로그와 시간을 맞출 수 있습니다.
-v / -vv상세 출력TTL·길이·IP 옵션까지 보입니다. 출력이 늘어납니다.
-X / -Ahex/ASCII 덤프본문이 노출됩니다. 민감정보에 주의합니다.
-s 0전체 길이 캡처(라이브)저장 크기가 커집니다.
-w파일 쓰기(라이브)승인이 필요하고 디스크 용량을 확인해야 합니다.

결과 판독

정상 출력
  • SYN → SYN-ACK → ACK 3-way가 짧은 간격으로 완결됩니다.
  • 종료는 FIN-ACK 교환 또는 정상 RST 1회입니다.
  • 외부 연결이 업무 시간대와 알려진 목적지에 집중됩니다.
이상 징후
  • 한 출발지에서 수십 개 포트로 SYN만 보냅니다(포트 스캔).
  • SYN에 대한 응답이 전부 RST입니다(닫힌 포트·방화벽 reject).
  • packets dropped by kernel 경고와 함께 RST가 반복됩니다.
  • 야간·주말에 낯선 외부 IP로 주기적 연결이 있습니다(비콘 의심).
오탐 주의
  • NAT·로드밸런서가 주소·포트를 재작성해 흐름이 어긋나 보입니다.
  • 헬스체크가 주기적 SYN을 보냅니다(정상).
  • 비대칭 라우팅으로 한 방향만 캡처됩니다.
  • 오프로드로 체크섬 오류·큰 패킷이 찍힙니다.
  • 캡처 시작·종료가 흐름 중간을 잘라 미완결로 보입니다.
조치
  • 스캔성 SYN은 출발지 자산과 점검 일정을 대조합니다(승인된 스캔일 수 있음).
  • 반복 RST·드롭은 방화벽 로그와 맞춰 정책을 확인합니다.
  • 비콘 의심 흐름은 호스트 프로세스·예약 작업을 확인합니다.
재점검
  • 조치 후 같은 위치에서 다시 캡처해 SYN·RST·재전송 건수를 비교합니다.
  • 필터별 건수를 표로 남겨 변화를 증명합니다.

샘플 증적 (마스킹)

443은 3-way가 완결됐고 8080은 RST로 거절됐습니다. [S]는 SYN만, [S.]는 SYN-ACK, [R.]은 RST-ACK입니다.

코드·컨테이너·IaC · 09

이미지·SBOM·IaC 스캔 결과 검토

고위험 취약점과 설정 오류를 조치 가능성 기준으로 정리합니다

Trivy · Kubescape 로컬 파일 읽기
점검 목적
로컬 이미지와 배포 매니페스트를 스캔해 실제로 고칠 수 있는 고위험 항목부터 정리합니다. 어떤 패키지가 어떤 취약점을 끌고 오는지 근거를 남깁니다.
검증 기준 버전
Trivy 0.50.1 · Kubescape 3.0.3
입력·대상
로컬 이미지 local/app:1.0 · SBOM sbom.json · 매니페스트 ./deploy
필요 권한
일반 사용자(로컬 이미지·파일 읽기) · Docker 데몬 접근 권한이 필요할 수 있음
실행 영향 등급
로컬 파일 읽기 이미지·파일을 읽습니다. 다만 Trivy는 기본적으로 취약점 DB 갱신을 위해 네트워크를 쓰므로, 오프라인 점검에서는 --skip-db-update로 로컬 캐시만 사용합니다.

대표 명령어

이미지 고위험만 로컬 파일 읽기 
trivy image --scanners vuln --severity HIGH,CRITICAL --ignore-unfixed local/app:1.0

--ignore-unfixed는 수정 버전이 없는 항목을 뺍니다. 지금 조치 가능한 것부터 보려는 기준입니다.

SBOM 만들기 로컬 파일 읽기 
trivy image --format cyclonedx --output sbom.json local/app:1.0

SBOM을 남기면 새 취약점이 공개됐을 때 재스캔만으로 영향을 확인할 수 있습니다.

SBOM 재스캔 로컬 파일 읽기 
trivy sbom --severity CRITICAL --skip-db-update sbom.json

이미지를 다시 받지 않고 구성 요소 기준으로 확인합니다.

Dockerfile·YAML 설정 로컬 파일 읽기 
trivy config --severity HIGH,CRITICAL ./deploy

권한·호스트 마운트·이미지 태그 같은 설정 오류를 봅니다.

매니페스트 통제 점검 로컬 파일 읽기 
kubescape scan framework nsa ./deploy/manifests --format pretty-printer

클러스터에 접속하지 않고 파일만 검사합니다.

옵션별 영향 해부

옵션의미부하·네트워크 / 파일 쓰기 / 민감정보 영향
--scanners vuln,secret,misconfig스캔 범위 선택범위를 넓히면 시간이 늘어납니다.
--severity등급 필터HIGH·CRITICAL부터 처리합니다.
--ignore-unfixed수정 버전 없는 항목 제외조치 가능성 기준으로 우선순위를 만듭니다.
--format table|json|cyclonedx|sarif출력 형식CI·SBOM·리뷰 도구와 연동합니다.
--skip-db-update / --offline-scanDB 갱신 생략네트워크 요청을 없애고 로컬 캐시만 사용합니다.
--exit-code 1발견 시 실패CI 게이트로 씁니다.
--timeout시간 상한큰 이미지에서 중단되지 않게 합니다.
--ignorefile예외 목록허용 근거(VEX)를 파일로 관리합니다.

결과 판독

정상 출력
  • HIGH/CRITICAL이 0이거나 모두 fixed 버전이 있습니다.
  • 베이스 이미지가 digest로 고정되어 있고 불필요 패키지가 적습니다.
  • Kubescape 결과에 critical 통제 위반이 없고 privileged·hostPath가 없습니다.
이상 징후
  • OS 패키지(openssl·glibc)에서 CRITICAL이 다수 나옵니다. 베이스 이미지 교체가 우선입니다.
  • fixed가 없는 항목이 대부분입니다. 상위 의존성·이미지 교체로만 해결됩니다.
  • secret 스캔에서 토큰·키가 나옵니다(이미지 레이어에 남음).
  • privileged: true, hostNetwork: true, :latest 태그가 있습니다.
  • Kubescape에서 hostPath·root 실행·capabilities 추가가 잡힙니다.
오탐 주의
  • distroless/scratch 이미지에서 패키지 정보를 못 읽어 '취약점 0'으로 보입니다.
  • 이미지에 실제 포함되지 않은 커널·런타임 공유 라이브러리 항목이 나옵니다.
  • VEX로 영향 없음이 확인된 항목이 계속 표시됩니다.
  • 멀티아키텍처 이미지에서 다른 아키텍처 레이어만 스캔합니다.
조치
  • 베이스 이미지를 최신 패치 버전으로 바꾸고 태그는 digest로 고정합니다.
  • 수정 버전이 있는 항목부터 패키지를 올리고, 없는 항목은 의존성 교체·격리로 대응합니다.
  • 매니페스트는 non-root·읽기 전용 루트·최소 capability로 조정합니다.
재점검
  • SBOM을 다시 만들어 같은 명령으로 재스캔하고 HIGH/CRITICAL 건수와 fixed 비율을 비교합니다.
  • CI에 --exit-code 1을 넣어 회귀를 막습니다.

샘플 증적 (마스킹)

취약점 번호와 버전은 표 형식을 보여 주기 위한 합성 값입니다. 실제 보고서에는 스캔 시각과 DB 버전이 함께 남습니다.

코드 패턴·시크릿 탐지 결과 검토

발견 항목이 실제로 도달 가능한지, 시크릿이 이력에 남았는지 확인합니다

Semgrep · Gitleaks 로컬 파일 읽기
점검 목적
로컬 저장소에서 인젝션·안전하지 않은 설정 같은 패턴과 하드코딩된 시크릿을 찾고, 발견 항목이 실제로 도달 가능한지 확인합니다. '발견 = 취약점'이 아니므로 근거 확인이 핵심입니다.
검증 기준 버전
Semgrep 1.60.1 · Gitleaks 8.18.2
입력·대상
로컬 저장소 작업 트리(./src)와 git 이력
필요 권한
일반 사용자 (파일 읽기)
실행 영향 등급
로컬 파일 읽기 로컬 파일과 이력만 읽습니다. Gitleaks의 기본 동작은 발견된 키를 외부 서비스로 검증하므로, 외부 요청을 막으려면 --no-verify를 씁니다.

대표 명령어

기본 룰셋 스캔 로컬 파일 읽기 
semgrep --config p/default --error --json --output semgrep.json src/

--error는 발견 시 종료 코드를 올려 CI 게이트로 쓸 수 있게 합니다.

OWASP 범주로 다시 로컬 파일 읽기 
semgrep --config p/owasp-top-ten src/

룰셋마다 잡는 범위가 다릅니다. 기본 룰에서 놓친 범주를 확인합니다.

새 발견만 로컬 파일 읽기 
semgrep --config auto --baseline-commit HEAD~1 src/

기준 커밋 이후 새로 생긴 발견만 남겨 기존 부채와 신규 유입을 구분합니다.

작업 트리 시크릿 로컬 파일 읽기 
gitleaks detect --source . --no-git --redact --report-format json --report-path leaks.json

--redact로 값은 보고서에서 가립니다. 보고서 파일도 민감정보로 취급합니다.

커밋 이력 시크릿 로컬 파일 읽기 
gitleaks detect --source . --log-opts 'HEAD~20..HEAD' --redact -v

시크릿은 지금 지워도 이력에 남습니다. 범위를 넓혀 확인합니다.

외부 검증 차단 로컬 파일 읽기 
gitleaks detect --source . --no-verify --redact

발견된 키로 외부 서비스에 검증 요청을 보내지 않습니다.

점검 목적

항목 상세 로컬 파일 읽기

항목 ID 하나의 근거와 권장 조치를 봅니다.

같은 경고 집계 로컬 파일 읽기 
sudo awk -F= '/^warning\[\]/{print $2}' /var/log/lynis-report.dat | sort | uniq -c | sort -rn

같은 경고가 여러 번 기록되는지 집계합니다.

버전·템플릿 경로 확인 로컬 파일 읽기 
nuclei -version

템플릿 자동 업데이트 경로까지 함께 출력됩니다. 결과 해석에는 템플릿 버전이 같이 남아야 합니다.

내 템플릿 문법만 검증 로컬 파일 읽기 
nuclei -validate -t templates/custom/

대상에 요청을 보내지 않고 YAML 문법·필수 필드만 확인합니다. 자체 템플릿을 쓰기 전에 먼저 돌립니다.

태그별 템플릿 목록 로컬 파일 읽기 
nuclei -tl -tags cve -severity critical,high

이번 점검에 실제로 적용될 템플릿을 미리 세어 봅니다. 예상보다 많으면 -t로 디렉터리를 좁힙니다.

고위험 템플릿만 실행 네트워크 요청 
nuclei -l targets.txt -severity high,critical -jsonl -o nuclei-out.jsonl -rl 10 -stats

-rl 10은 초당 요청 10건 상한입니다. -stats는 진행 상황만 stderr로 보여 주고 결과 파일에는 들어가지 않습니다.

심각도별 결과 추리기 로컬 파일 읽기 
jq -r 'select(.info.severity=="critical") | [.host,.matched-at,.info.name] | @tsv' nuclei-out.jsonl

결과 파일은 JSONL(한 줄에 한 객체)입니다. jq로 필드를 골라 표로 만들면 보고서에 그대로 붙일 수 있습니다.

로컬 설정 확인 로컬 파일 읽기 
cat ~/.config/nuclei/config.yaml

rate-limit·templates·interactsh 설정이 남아 있으면 실행 영향이 달라집니다. 점검 전에 값을 확인합니다.

옵션별 영향 해부

옵션의미부하·네트워크 / 파일 쓰기 / 민감정보 영향
-l, -list대상 목록 파일파일 한 줄이 대상 하나입니다. 승인 범위 밖 주소가 섞이지 않았는지 먼저 확인합니다.
-t, -templates템플릿 경로·디렉터리지정하지 않으면 커뮤니티 템플릿 전체가 적용되어 요청 수가 크게 늘어납니다.
-tags / -severity템플릿 필터조건은 AND로 묶입니다. 필터를 좁힐수록 요청 수와 오탐이 함께 줄어듭니다.
-jsonlJSONL 결과 출력줄 단위로 스트리밍되어 중간에 끊겨도 앞부분을 판독할 수 있습니다.
-o, -output결과 파일증적 보관용입니다. 파일에는 curl-command·matched-at이 함께 남습니다.
-rl, -rate-limit초당 요청 상한운영 대상에서 부하·차단을 줄이는 핵심 옵션입니다. 기본값은 무제한에 가깝습니다.
-c, -concurrency동시 템플릿 수올리면 빨라지지만 대상 서버 연결 수가 그만큼 늘어납니다.
-duc템플릿 자동 업데이트 생략재현성 있는 점검에 필요합니다. 실행마다 템플릿이 바뀌면 결과 비교가 어긋납니다.
-sarif-exportSARIF 보고서코드 스캐닝 도구가 읽는 형식입니다. 같은 결과를 두 형식으로 남길 때 씁니다.

결과 판독

정상 출력
  • 결과가 0건이면 '취약 없음'이 아니라 '이 템플릿들이 매칭되지 않음'으로 기록합니다. 적용 템플릿 목록과 함께 남겨야 의미가 있습니다.
  • info.severity가 info인 결과(기술 탐지·헤더 누락)는 취약점이 아니라 자산 정보로 분류합니다.
  • 같은 template-id가 여러 matched-at에 나오면 한 호스트의 반복인지 여러 호스트인지 묶어 셉니다.
이상 징후
  • severity: critical 템플릿이 매칭되고 curl-command 재현에서도 같은 응답이 나옵니다.
  • matcher-name이 word·status만으로 된 결과는 응답 한 조각만 본 것이므로 본문 전체를 확인합니다.
  • 결과에 다른 테넌트·다른 도메인의 응답이 섞여 있습니다. 리다이렉트·가상호스트 설정을 확인합니다.
오탐 주의
  • WAF·CDN의 차단 페이지가 템플릿 단어와 우연히 일치해 매칭되는 경우가 있습니다. 상태 코드와 server 헤더를 함께 봅니다.
  • 커스텀 404가 200으로 응답하는 대상에서는 '존재' 계열 템플릿이 모두 매칭됩니다.
  • 템플릿이 오래되면 패치된 제품에도 매칭됩니다. template-id의 공개일과 제품 버전을 대조합니다.
  • -duc 없이 실행하면 점검 도중 템플릿이 갱신되어 같은 명령의 결과가 달라질 수 있습니다.
조치
  • 매칭 결과는 재현 요청으로 확인한 뒤 '확인된 취약'과 '확인 필요'로 나눠 보고합니다.
  • 자체 템플릿은 -validate를 통과한 것만 쓰고, matcher 조건을 코드 리뷰로 검토합니다.
  • 운영 스캔은 -rl과 시간 창을 정하고, 차단 임계값이 낮은 대상은 별도 창에서 실행합니다.
재점검
  • 같은 템플릿 버전·같은 필터로 다시 돌려 template-id+matched-at 집합을 이전 결과와 비교합니다.
  • 조치 후 재현 요청이 차단되는지, 결과 파일에서 해당 조합이 사라졌는지 함께 확인합니다.

샘플 증적 (마스킹)

첫 두 줄은 정보성 결과, 셋째 줄이 확인이 필요한 고위험 매칭입니다. curl-command로 재현한 뒤에만 '확인된 취약'으로 올립니다.

디렉터리·파라미터 후보 탐색 결과 판독

워드리스트로 후보를 좁히되 응답 크기·상태 코드 필터로 가짜 200을 걸러 내는 판독 기준

ffuf · feroxbuster 네트워크 요청
점검 목적
승인된 테스트 서버에서 숨은 경로·파라미터 후보를 좁히고, 같은 크기·같은 제목의 응답을 필터로 걷어내 실제 존재하는 경로만 남깁니다. 퍼징은 요청량이 크므로 범위·속도 상한이 먼저입니다.
검증 기준 버전
ffuf v2.1 계열 · feroxbuster 2.11 계열
입력·대상
로컬 워드리스트 wordlist-small.txt (100줄 이내) · 대상 http://127.0.0.1:8080/FUZZ
필요 권한
일반 사용자
실행 영향 등급
네트워크 요청 워드 수 × 요청 수만큼 트래픽이 발생합니다. -rate·-t로 상한을 두고, 운영 대상은 사전 협의된 시간 창에서만 실행합니다.

보고서 필드

JSON(-of json) · CSV · HTML

필드의미판독 포인트
input.FUZZ시도한 값워드리스트 위치와 함께 기록해야 재현됩니다.
status응답 코드301·403도 존재 신호입니다. 200만 보면 놓칩니다.
length / words / lines응답 크기 지표가짜 200을 걸러 내는 기준입니다.
redirectlocation리다이렉트 대상같은 위치로만 튀면 폴백 페이지일 수 있습니다.

대표 명령어

버전 확인 로컬 파일 읽기 
ffuf -V

결과 JSON 필드 구성이 버전마다 조금씩 다릅니다. 증적에는 버전을 함께 남깁니다.

옵션 요약 확인 로컬 파일 읽기 
ffuf -h | head -40

-mc·-fc·-fs의 기본값을 확인합니다. 필터를 모르고 돌리면 노이즈가 그대로 쌓입니다.

상한을 둔 디렉터리 탐색 네트워크 요청 
ffuf -u http://127.0.0.1:8080/FUZZ -w wordlist-small.txt -mc 200,204,301,302,307,401,403 -fs 0 -rate 20 -t 10 -o ffuf-out.json -of json

-rate 20은 초당 20요청, -t 10은 동시 연결 10개입니다. -fs 0은 길이 0인 응답을 결과에서 뺍니다.

결과 표로 추리기 로컬 파일 읽기 
jq -r '.results[] | [.status, .length, .words, .url] | @tsv' ffuf-out.json

같은 length가 반복되면 SPA 폴백·커스텀 404일 가능성이 큽니다. 크기별로 묶어 먼저 봅니다.

feroxbuster 로 같은 범위 재확인 네트워크 요청 
feroxbuster -u http://127.0.0.1:8080 -w wordlist-small.txt --filter-status 404 --json --output ferox.json --rate-limit 20 --no-recursion

재귀를 끄고 한 단계만 봅니다. 두 도구의 결과가 다르면 워드리스트·필터 차이를 먼저 확인합니다.

ferox 결과 판독 로컬 파일 읽기 
jq -r 'select(.type=="response") | [.status, .content_length, .url] | @tsv' ferox.json

feroxbuster JSON은 type으로 응답·설정·에러를 구분합니다. response만 골라야 표가 깔끔합니다.

옵션별 영향 해부

옵션의미부하·네트워크 / 파일 쓰기 / 민감정보 영향
-w워드리스트줄 수가 곧 요청 수입니다. 승인된 목록인지, 중복이 없는지 확인합니다.
-mc / -fc포함·제외 상태 코드-mc all은 모든 코드를 결과로 남겨 노이즈가 커집니다.
-fs길이로 제외가짜 200의 크기를 알 때 가장 효과적입니다. -fl(줄), -fw(단어)도 같은 방식입니다.
-rate초당 요청 상한대상 부하와 차단 위험을 직접 줄입니다. 0은 무제한입니다.
-t동시 연결 수처리량을 올리지만 서버 연결·로그 부담도 함께 올라갑니다.
-o / -of결과 파일·형식json·csv·html·md를 지원합니다. 보고서에는 json을 원본으로 남깁니다.
-recursion / -recursion-depth재귀 탐색요청 수가 곱절로 늘어납니다. 승인 범위에 하위 경로가 포함될 때만 씁니다.
-maxtime전체 실행 상한(초)작업 창을 넘기지 않게 하는 안전장치입니다.
-H / -X / -d헤더·메서드·본문인증 쿠키를 넣으면 권한 밖 경로까지 탐색될 수 있어 테스트 계정으로만 씁니다.

결과 판독

정상 출력
  • 서로 다른 length를 가진 소수 결과만 남고, 나머지는 -fs 필터로 사라집니다.
  • 301은 실제 디렉터리, 403은 존재하지만 접근이 막힌 경로로 구분해 기록합니다.
  • 같은 크기의 결과가 수백 건이면 필터가 부족한 상태입니다. 워드리스트를 줄이거나 크기 필터를 추가합니다.
이상 징후
  • 모든 후보가 200이고 크기가 비슷합니다. SPA 폴백이나 커스텀 404를 결과로 오인한 상태입니다.
  • 429가 섞여 나옵니다. 속도 상한을 넘겨 일부 경로를 못 본 것이므로 상한을 낮춰 다시 돌립니다.
  • -mc all로 돌린 결과에 5xx가 대량으로 섞여 있습니다. 서버 오류를 '존재'로 읽지 않습니다.
오탐 주의
  • 와일드카드 DNS·가상호스트가 모든 이름에 같은 응답을 주면 전부 존재로 보입니다.
  • WAF가 차단하며 같은 페이지를 주면 403이 대량으로 잡힙니다. 차단 로그와 대조합니다.
  • 리다이렉트를 따라가지 않는 기본 설정에서는 302의 최종 목적지를 알 수 없습니다.
  • 두 도구의 워드리스트가 다르면 결과 차이가 취약점 차이로 보일 수 있습니다.
조치
  • 실제 존재하는 경로만 목록화하고, 인증 없이 열린 경로는 별도 조치 대상으로 올립니다.
  • 디렉터리 목록 노출·백업 파일처럼 설정으로 막을 수 있는 항목은 서버 설정에서 먼저 처리합니다.
  • 탐색량 자체를 줄이도록 불필요한 경로·기본 페이지를 정리합니다.
재점검
  • 같은 워드리스트·같은 필터로 다시 돌려 결과 URL 집합을 비교합니다.
  • 조치한 경로가 404 또는 차단으로 바뀌었는지 상태 코드로 확인합니다.

샘플 증적 (마스킹)

301은 디렉터리 존재, 403은 접근 차단입니다. 크기가 다른 두 결과만 남았으므로 필터가 의도대로 동작한 상태입니다.

SQL 삽입 의심 지점 확인과 세션 기록 판독

테스트 대상의 파라미터 하나를 낮은 level·risk로 확인하고, 저장된 세션 로그에서 판정 근거만 읽습니다

sqlmap 네트워크 요청

sqlmap -hh | sed -n '1,40p'

--parse-errors·--flush-session처럼 판독에 영향을 주는 옵션을 먼저 확인합니다.

파라미터 1개 최소 강도 확인 네트워크 요청 
sqlmap -u "http://127.0.0.1:8080/items?id=1" --batch --level 1 --risk 1 --technique=B --threads 1 --timeout 10

--technique=B는 불리언 기반만 시도합니다. --batch는 질문에 기본값으로 답해 무인 실행합니다.

저장된 프록시 로그로 대상 지정 로컬 파일 읽기 
sqlmap -l burp-proxy.log --batch --level 1 --risk 1 --output-dir sqlmap-out

직접 요청을 만들지 않고 이미 저장된 트래픽의 요청을 그대로 씁니다. 로그에 승인 범위 밖 대상이 없는지 먼저 확인합니다.

세션 기록 확인 로컬 파일 읽기 
grep -nE 'Parameter:|Type:|heuristic|CRITICAL' sqlmap-out/127.0.0.1/log

출력 디렉터리는 대상별로 나뉩니다. log가 판정 근거의 원본입니다.

INI 설정 재사용 로컬 파일 읽기 
sqlmap -c sqlmap.conf --batch

팀에서 정한 timeout·threads·technique 조합을 고정해 실행 편차를 줄입니다.

옵션별 영향 해부

옵션의미부하·네트워크 / 파일 쓰기 / 민감정보 영향
--batch무인 실행질문에 기본값으로 답합니다. 위험한 기본값이 있는지 먼저 확인해야 합니다.
--level시도 범위(1~5)올릴수록 헤더·쿠키까지 확장되고 요청 수와 오탐이 늘어납니다.
--risk위험한 기법 허용(1~3)3은 OR 기반 등 데이터에 부담을 주는 기법을 포함합니다.
--technique기법 선택B(불리언)·E(에러)·T(시간) 등을 좁혀 요청 수를 줄입니다.
--threads동시 요청 수올리면 서버 부하와 잠금 위험이 커집니다. 테스트에서는 1~2로 둡니다.
--parse-errorsDB 오류 메시지 파싱에러 기반 판별의 근거를 로그에 남깁니다.
--flush-session세션 초기화이전 결과 캐시를 지웁니다. 재점검 때 오래된 판정이 재사용되는 것을 막습니다.
--output-dir결과 디렉터리대상별 log·세션 파일이 남아 증적으로 쓸 수 있습니다.
-l / -r프록시 로그·요청 파일이미 저장된 트래픽으로 대상을 지정합니다. 요청을 새로 만들지 않습니다.

결과 판독

정상 출력
  • [CRITICAL] all tested parameters do not appear to be injectable로 끝나고 Parameter: 항목이 없습니다.
  • testing if GET parameter 'id' is dynamic 단계에서 값이 고정이라고 나오면 판정 대상이 아닙니다.
  • 세션 로그에 사용한 기법·level·risk가 그대로 남아 재현 조건이 명확합니다.
이상 징후
  • Parameter: id (GET) 아래 Type: boolean-based blind가 나오고 응답 차이가 재현됩니다.
  • heuristic (basic) test shows that ... might be injectable이 나온 뒤 확정 기법이 없습니다. 의심 단계입니다.
  • DBMS 배너·에러 메시지가 로그에 남았습니다. 정보 노출 자체가 조치 대상입니다.
오탐 주의
  • heuristic 문구만 보고 취약으로 단정하면 안 됩니다. 확정 Type:과 재현 응답을 함께 봅니다.
  • WAF가 모든 요청을 차단하면 '주입 불가'로 보이지만 실제로는 검사되지 않은 상태입니다.
  • level·risk를 올리면 우연한 응답 차이로 오탐이 늘어납니다. 기본 강도 결과를 먼저 신뢰합니다.
  • --flush-session 없이 재실행하면 이전 세션 판정이 그대로 재사용됩니다.
조치
  • 파라미터 바인딩(Prepared Statement)으로 쿼리를 분리하고, 동적 정렬·컬럼명은 허용 목록으로 제한합니다.
  • DB 오류 메시지를 사용자 응답에서 제거하고 상세 로그는 서버에만 남깁니다.
  • WAF는 보조 수단으로만 두고 코드 수정을 완료 조건으로 삼습니다.
재점검
  • 같은 요청·같은 --technique로 다시 실행해 Parameter: 항목이 사라졌는지 확인합니다.
  • 에러 응답이 일반화되었는지, 응답 시간 편차가 사라졌는지 함께 봅니다.

샘플 증적 (마스킹)

휴리스틱 의심 문구가 있어도 확정 기법이 없으면 취약으로 보고하지 않습니다. 마지막 CRITICAL 줄이 최종 판정입니다.

웹 서버 구성·노출 파일 점검 보고서 판독

서버 헤더·기본 파일·오래된 구성 요소 신호를 JSON 보고서로 받아 항목별로 걸러 읽습니다

nikto 네트워크 요청
점검 목적
테스트 서버가 어떤 구성 정보를 노출하고 어떤 기본 파일이 남아 있는지 빠르게 훑고, 보고서 항목을 '설정 문제'와 '정보 노출'로 나눠 읽습니다.
검증 기준 버전
nikto 2.6.1 계열
입력·대상
로컬 테스트 서버 http://127.0.0.1:8080 · 로컬 설정 nikto.conf
필요 권한
일반 사용자
실행 영향 등급
네트워크 요청 플러그인 조합에 따라 수백~수천 건의 요청이 나갑니다. -Tuning으로 범위를 좁히고 -maxtime으로 시간 상한을 둡니다.

보고서 필드

JSON(-Format json) · CSV · XML

필드의미판독 포인트
idNikto 항목 번호같은 번호는 같은 점검 항목입니다.
method사용한 메서드GET/POST 등 요청 방식을 보여 줍니다.
url발견 경로쿼리스트링까지 포함됩니다.
msg발견 내용설정 문제·정보 노출·존재 여부를 구분해 읽습니다.

대표 명령어

버전·플러그인 DB 확인 로컬 파일 읽기 
nikto -Version

플러그인 DB 버전이 오래되면 최신 제품의 기본 파일을 놓칩니다.

플러그인 목록 로컬 파일 읽기 
nikto -list-plugins | head -20

테스트를 수행하지 않고 사용 가능한 점검 항목만 보여 줍니다.

구성·정보 노출만 점검 네트워크 요청 
nikto -h http://127.0.0.1:8080 -nointeractive -nocheck -maxtime 60s -Tuning 23 -o nikto-out.json -Format json

-Tuning 23은 오설정(2)·정보 노출(3)만 봅니다. -nocheck은 시작 시 업데이트 확인을 생략합니다.

보고서 항목 표로 추리기 로컬 파일 읽기 
jq -r '.vulnerabilities[] | [.id, .method, .url, .msg] | @tsv' nikto-out.json

id는 Nikto 항목 번호입니다. 같은 id가 여러 URL에 반복되면 패턴으로 묶어 봅니다.

상세 출력으로 원문 확인 네트워크 요청 
nikto -h http://127.0.0.1:8080 -nointeractive -nocheck -Display V -maxtime 30s

-Display V는 요청·응답을 상세히 보여 줍니다. 오탐 판단은 이 출력으로 합니다.

로컬 설정 확인 로컬 파일 읽기 
grep -vE '^#|^$' nikto.conf | head -30

프록시·User-Agent·타임아웃 기본값이 들어 있습니다. 팀 표준과 다른 값이 있으면 실행 결과가 달라집니다.

옵션별 영향 해부

옵션의미부하·네트워크 / 파일 쓰기 / 민감정보 영향
-h, -host대상 호스트·URL포트를 지정하지 않으면 80을 씁니다. HTTPS는 -ssl 또는 URL 스킴으로 지정합니다.
-Tuning점검 범위 선택x를 붙이면 제외 의미가 됩니다. 주입(4)·SQLi(9)는 별도 도구로 확인하는 편이 낫습니다.
-maxtime호스트당 최대 시간작업 창을 넘기지 않게 합니다. 시간이 모자라면 일부 항목이 미점검으로 남습니다.
-o / -Format결과 파일·형식json·csv·xml·htm을 지원합니다. 확장자만으로 형식이 정해지기도 합니다.
-nointeractive대화형 기능 끄기자동화에 필요합니다. 남겨 두면 프롬프트에서 멈출 수 있습니다.
-nocheck업데이트 확인 생략외부로 나가는 요청을 줄이고 실행 시간을 예측 가능하게 만듭니다.
-Display표시 수준V(상세)·P(진행)·S(IP 마스킹) 등을 조합합니다. 증적 공유 시 S가 유용합니다.
-evasion우회 인코딩탐지 회피용으로 요청을 변형합니다. 오탐이 늘고 WAF 로그가 지저분해집니다.
-404code / -404string가짜 404 기준커스텀 404를 음성 응답으로 처리해 오탐을 줄입니다.

결과 판독

정상 출력
  • + Server: nginx처럼 헤더 1~2건만 정보성으로 남고 기본 파일 발견은 없습니다.
  • 0 host(s) tested는 정상이 아니라 연결 실패입니다. 대상·포트를 다시 확인합니다.
  • -Tuning 23 결과에 id가 소수만 남고 모두 설정 관련 항목입니다.
이상 징후
  • /admin/·/backup.zip·.git/ 같은 경로가 발견 목록에 올라옵니다.
  • X-Powered-By·Server 버전이 그대로 노출되어 패치 수준을 추정할 수 있습니다.
  • OSVDB/id 항목이 수십 건 반복됩니다. 같은 원인(디렉터리 목록·기본 페이지)인지 묶어 봅니다.
오탐 주의
  • 커스텀 404가 200으로 응답하면 모든 후보가 '발견'으로 잡힙니다. -404code·-404string으로 기준을 맞춥니다.
  • CDN·WAF가 동일 페이지를 돌려주면 경로 차이가 사라집니다. 응답 본문 해시로 비교합니다.
  • 오래된 플러그인 DB는 이미 삭제된 파일을 계속 보고합니다. -dbcheck로 DB 상태를 확인합니다.
  • -evasion을 켜면 인코딩된 요청이 우연히 다른 응답을 받아 오탐이 늘어납니다.
조치
  • 기본 파일·백업·.git 노출은 서버 설정에서 차단하고 배포 산출물에서 제거합니다.
  • 버전 노출 헤더는 최소화하고, 실제 패치 상태는 패키지 버전으로 따로 확인합니다.
  • 디렉터리 목록 자동 생성 기능을 끄고 불필요한 기본 페이지를 삭제합니다.
재점검
  • 같은 -Tuning으로 다시 돌려 id+url 집합을 비교합니다.
  • 조치한 경로가 404로 바뀌었는지, 헤더에서 버전이 사라졌는지 확인합니다.

샘플 증적 (마스킹)

첫 항목은 관리자 페이지 존재, 둘째는 버전·제품 정보 노출입니다. 둘 다 '취약점'이 아니라 조치 대상 노출로 분류합니다.

서브도메인 자산 목록 수집과 범위 확인

공개 소스에서 서브도메인을 모아 승인 범위 안의 자산만 남기고, 와일드카드·서드파티 신호를 걸러 냅니다

subfinder 네트워크 요청
점검 목적
점검 전에 대상 조직의 서브도메인 후보를 모아 승인 범위와 대조합니다. 수집 자체가 수동 소스에 질의를 보내므로, 범위 밖 도메인을 넣지 않는 것이 첫 단계입니다.
검증 기준 버전
subfinder v2.7 계열
입력·대상
승인된 도메인 fixture.test · 범위 목록 in-scope-domains.txt
필요 권한
일반 사용자 (설정 파일 읽기 권한)
실행 영향 등급
네트워크 요청 수동 소스(인증서 투명성 로그·검색 인덱스 등)에 도메인 이름이 질의됩니다. 승인 범위 밖 도메인은 조회하지 않습니다.

보고서 필드

TXT(기본) · JSONL(-json)

필드의미판독 포인트
host발견된 이름범위 대조의 기본 키입니다.
source발견 소스출처가 하나뿐인 이름은 오탐일 수 있습니다.
input질의한 루트 도메인범위 목록과 일치하는지 확인합니다.

대표 명령어

버전 확인 로컬 파일 읽기 
subfinder -version

소스 플러그인 구성이 버전마다 다릅니다. 결과 수 비교에는 버전이 필요합니다.

단일 도메인 수집 네트워크 요청 
subfinder -d fixture.test -silent -o subdomains.txt -timeout 5

-silent는 배너를 빼고 결과만 남깁니다. 5초 타임아웃으로 느린 소스를 끊습니다.

중복 제거·개수 로컬 파일 읽기 
sort -u subdomains.txt | wc -l

여러 소스가 같은 이름을 주므로 중복이 흔합니다. 범위 대조 전에 정리합니다.

범위 목록으로 일괄 수집 네트워크 요청 
subfinder -dL in-scope-domains.txt -all -silent -o subdomains-all.txt -rl 5

-all은 느린 소스까지 포함합니다. -rl 5로 초당 질의를 제한합니다.

JSONL 로 근거 남기기 네트워크 요청 
subfinder -d fixture.test -silent -json -o subdomains.jsonl

source 필드가 있어 어떤 소스에서 나왔는지 추적할 수 있습니다.

소스 자격증명 설정 확인 로컬 파일 읽기 
cat ~/.config/subfinder/provider-config.yaml

유료 API 키가 들어 있을 수 있으므로 화면 공유·증적에는 값을 가립니다.

옵션별 영향 해부

옵션의미부하·네트워크 / 파일 쓰기 / 민감정보 영향
-d도메인 하나승인 범위의 루트 도메인만 넣습니다.
-dL도메인 목록 파일여러 도메인을 한 번에. 범위 목록과 실제 파일이 같은지 먼저 확인합니다.
-all느린 소스 포함결과는 늘지만 실행 시간과 외부 질의 수가 커집니다.
-recursive재귀 수집발견된 서브도메인의 하위 이름까지 봅니다. 요청량이 늘어납니다.
-jsonJSONL 출력host·source 필드로 근거를 남깁니다.
-silent배너 생략파이프라인에 넣기 좋은 형태로 결과만 출력합니다.
-rl초당 질의 상한외부 소스의 속도 제한을 피합니다.
-timeout소스별 타임아웃(초)느린 소스 하나가 전체를 붙잡지 않게 합니다.
-pc소스 설정 파일API 키 경로를 바꿉니다. 키는 저장소에 두지 않습니다.

결과 판독

정상 출력
  • 승인 범위 도메인의 하위 이름만 나오고, 각 이름이 실제 DNS로 해석됩니다.
  • source가 둘 이상인 이름은 신뢰도가 높습니다.
  • 수집 수가 예상보다 적으면 소스 API 키 미설정을 먼저 확인합니다.
이상 징후
  • 범위 밖 도메인·타사 SaaS 기본 도메인이 섞여 있습니다. 범위 목록을 다시 확인합니다.
  • *.fixture.test 같은 와일드카드 응답이 모든 이름에 대해 같은 IP를 줍니다.
  • CNAME이 외부 SaaS를 가리키는 이름이 있습니다. 서비스 이전·만료 여부를 확인합니다.
오탐 주의
  • 와일드카드 DNS가 켜져 있으면 무작위 이름도 '존재'로 수집됩니다.
  • 공개 인증서 로그에는 폐기된 이름이 오래 남습니다. 현재 DNS와 대조합니다.
  • 서드파티가 관리하는 기본 도메인은 조직 자산이 아닐 수 있습니다.
  • 범위 목록 파일에 이전 프로젝트 도메인이 남아 있으면 결과가 오염됩니다.
조치
  • 확인된 자산 목록을 자산 대장과 대조하고, 대장에 없는 이름은 소유·용도를 확인합니다.
  • 만료·미사용 이름은 DNS 레코드를 제거해 서브도메인 탈취를 막습니다.
재점검
  • 같은 -dL 목록으로 다시 수집해 새로 생긴 이름과 사라진 이름을 비교합니다.
  • 조치한 이름이 더 이상 해석되지 않는지 dig로 확인합니다.

샘플 증적 (마스킹)

다섯 이름 모두 승인 범위 안입니다. cdn·status처럼 외부 SaaS로 CNAME이 걸린 이름은 소유 관계를 따로 확인합니다.

수집한 호스트의 응답 상태·기술 스택 확인

서브도메인 목록을 살아 있는 웹 서비스로 좁히고, 상태 코드·제목·기술 스택을 JSONL로 남깁니다

httpx 네트워크 요청
점검 목적
수집한 이름 중 실제로 응답하는 웹 서비스만 남기고, 서버·프레임워크·CDN 신호를 붙여 이후 점검 대상을 정합니다. 응답만 보는 단계이므로 취약점 판정은 하지 않습니다.
검증 기준 버전
httpx v1.7 계열
입력·대상
저장된 호스트 목록 hosts.txt (예: fixture.test, 127.0.0.1:8080)
필요 권한
일반 사용자
실행 영향 등급
네트워크 요청 호스트 수만큼 요청이 나갑니다. -rl·-threads로 상한을 두고, 인증이 필요한 서비스는 테스트 계정으로만 접근합니다.

보고서 필드

JSONL(-json) · TXT

필드의미판독 포인트
url / input요청·원본 입력리다이렉트 후 URL과 입력이 다를 수 있습니다.
status_code최종 상태기본값은 200·302 계열만 남습니다.
title페이지 제목기본 페이지·로그인 화면 식별에 씁니다.
tech탐지된 기술추정값입니다. 버전 확정 근거로 쓰지 않습니다.
webserver서버 헤더CDN 뒤에서는 실제 서버와 다릅니다.

대표 명령어

버전 확인 로컬 파일 읽기 
httpx -version

출력 필드 이름이 버전에 따라 달라질 수 있어 증적에 버전을 남깁니다.

상태·제목·기술 스택 수집 네트워크 요청 
httpx -l hosts.txt -silent -status-code -title -tech-detect -web-server -json -o httpx-out.jsonl -rl 10 -timeout 5

-json은 JSONL입니다. -rl 10으로 초당 요청을 제한합니다.

오류 응답만 추리기 로컬 파일 읽기 
jq -r 'select(.status_code >= 500) | [.url, .status_code, .title] | @tsv' httpx-out.jsonl

5xx는 서비스 상태 문제일 뿐 취약점이 아닙니다. 별도 목록으로 분리합니다.

기술 스택 목록화 로컬 파일 읽기 
jq -r 'select(.tech != null) | [.url, (.tech | join(","))] | @tsv' httpx-out.jsonl

스택 정보는 버전 추정의 출발점이며, 실제 버전은 별도 확인이 필요합니다.

응답 본문 저장 네트워크 요청 
httpx -u http://127.0.0.1:8080 -sr -srd http-out -silent

-sr은 응답을, -srd는 저장 디렉터리를 지정합니다. 본문에 개인정보가 있으면 증적 공유 전에 가립니다.

로컬 설정 확인 로컬 파일 읽기 
httpx -config httpx.conf -l hosts.txt -silent

프록시·헤더·타임아웃 기본값을 팀 표준으로 고정합니다.

옵션별 영향 해부

옵션의미부하·네트워크 / 파일 쓰기 / 민감정보 영향
-l입력 목록한 줄에 하나. 파이프 입력도 가능합니다.
-jsonJSONL 출력필드 단위 후처리에 필요합니다.
-status-code / -title상태·제목 표시기본 페이지 식별에 가장 실용적인 조합입니다.
-tech-detect기술 스택 탐지응답 패턴 기반 추정입니다. 버전까지 확정하지 않습니다.
-web-server서버 헤더프록시·CDN 뒤 실제 서버와 다를 수 있습니다.
-mc / -fc포함·제외 코드기본값은 200·302 계열만 포함합니다. 403도 보려면 -mc all 후 필터링합니다.
-rl / -threads속도·동시성대상 부하를 직접 좌우합니다.
-follow-redirects리다이렉트 추적최종 목적지와 상태를 함께 봐야 할 때 켭니다.

결과 판독

정상 출력
  • 응답하는 호스트만 남고 status_code가 200·301·302로 정리됩니다.
  • title이 비어 있는 항목은 API·정적 자원일 수 있으므로 content-type으로 구분합니다.
  • tech가 nginx·React처럼 일반적인 조합으로 나옵니다.
이상 징후
  • 인증 없이 접근 가능한 관리 콘솔·대시보드 제목이 보입니다.
  • server 헤더에 버전이 그대로 노출됩니다.
  • 같은 title·같은 크기가 수십 호스트에서 반복됩니다. 와일드카드·CDN 기본 페이지일 수 있습니다.
오탐 주의
  • 리다이렉트를 추적하지 않으면 301만 보이고 실제 서비스는 보이지 않습니다.
  • WAF가 403을 주면 '없는 호스트'로 오인합니다. 차단 로그와 대조합니다.
  • tech는 응답 패턴 추정이라 오탐이 있습니다. 취약점 판정 근거로 쓰지 않습니다.
  • 기본 페이지가 200을 주면 살아 있는 서비스로 오인합니다.
조치
  • 살아 있는 서비스 목록을 자산 대장과 맞추고, 인증 없이 열린 관리 화면을 우선 조치합니다.
  • 불필요한 기본 페이지·디렉터리 목록을 제거하고 서버 버전 노출을 줄입니다.
재점검
  • 같은 hosts.txt로 다시 돌려 url+status_code 집합을 비교합니다.
  • 조치한 호스트가 401·403·404로 바뀌었는지 확인합니다.

샘플 증적 (마스킹)

제목이 빈 두 번째 항목은 API, 403인 세 번째는 차단된 관리 화면입니다. 403도 자산 존재 신호이므로 버리지 않습니다.

TLS 구성·취약 프로토콜 점검 결과 판독

프로토콜·암호군·인증서·알려진 취약점 신호를 JSON으로 받아 심각도별로 걸러 읽습니다

testssl.sh 네트워크 요청
점검 목적
테스트 서버가 어떤 TLS 버전·암호군을 허용하고 인증서가 유효한지 확인하고, 알려진 취약점 신호를 심각도로 정렬해 조치 우선순위를 정합니다.
검증 기준 버전
testssl.sh 3.2 계열 (--jsonfile·--severity 기준)
입력·대상
로컬 테스트 서버 https://fixture.test · 127.0.0.1:8443
필요 권한
일반 사용자
실행 영향 등급
네트워크 요청 TLS 핸드셰이크를 수백 회 반복합니다. DNS 조회·CRL 확인 외에는 제3자에게 요청하지 않습니다. --fast로 범위를 줄일 수 있습니다.

보고서 필드

JSON(--jsonfile) · CSV · HTML

필드의미판독 포인트
id점검 항목TLS1·HSTS·cert_expirationStatus 등입니다.
severity항목 심각도OK·INFO·LOW~CRITICAL로 정렬해 봅니다.
finding판정 문장제품이 아니라 이 문장이 근거입니다.
cve관련 CVE있을 때만 채워집니다. 패치 수준 확인에 씁니다.

대표 명령어

버전·OpenSSL 확인 로컬 파일 읽기 
testssl.sh --version

사용하는 OpenSSL 빌드에 따라 검사 가능한 암호군이 달라집니다.

주요 옵션 확인 로컬 파일 읽기 
testssl.sh --help | head -40

--severity·--fast·출력 형식 옵션을 먼저 확인합니다.

요약 점검 + JSON 저장 네트워크 요청 
testssl.sh --fast --severity MEDIUM --jsonfile testssl-out.json --color 0 --quiet https://fixture.test

--fast는 일부 암호군 검사를 생략합니다. --color 0은 로그용 무색 출력입니다.

심각도 높은 항목만 로컬 파일 읽기 
jq -r '.[] | select(.severity=="CRITICAL" or .severity=="HIGH") | [.id, .finding] | @tsv' testssl-out.json

JSON은 항목 객체의 배열입니다. id가 점검 항목, finding이 판정 문장입니다.

프로토콜 항목만 로컬 파일 읽기 
jq -r '.[] | select(.id=="TLS1" or .id=="TLS1_1") | [.id, .severity, .finding] | @tsv' testssl-out.json

구버전 프로토콜 허용 여부는 조치 우선순위가 높은 항목입니다.

로컬 포트 직접 점검 네트워크 요청 
testssl.sh --protocols --color 0 127.0.0.1:8443

SNI가 필요한 가상호스트는 --sni로 이름을 지정해야 올바른 인증서를 봅니다.

옵션별 영향 해부

옵션의미부하·네트워크 / 파일 쓰기 / 민감정보 영향
--jsonfileJSON 결과 파일사후 분석·비교의 원본입니다. --json-pretty로 읽기 좋게 만들 수 있습니다.
--severity출력 최소 심각도화면·파일 출력을 좁힙니다. 검사 자체를 줄이지는 않습니다.
--fast빠른 점검암호군 전수 검사 등 일부 항목을 생략합니다. 누락 항목을 보고서에 적습니다.
--protocols프로토콜만실행 시간을 크게 줄입니다. 반복 점검에 적합합니다.
--vulnerable취약점 항목만알려진 결함(Heartbleed 등) 항목만 확인합니다.
--starttlsSTARTTLS 협상SMTP·IMAP 등 평문 포트에서 TLS를 시작하는 서비스에 필요합니다.
--sniSNI 이름 지정가상호스트별 인증서를 구분합니다.
--file대상 목록 일괄 실행여러 대상을 순차·병렬 점검합니다. 승인 범위 목록과 같은지 확인합니다.
--color 0 / --quiet무색·조용히로그·증적에 ANSI 코드가 섞이지 않게 합니다.

결과 판독

정상 출력
  • TLS1·TLS1_1이 not offered이고 TLS 1.2·1.3만 허용됩니다.
  • 인증서 체인이 검증되고 만료일이 충분히 남아 있습니다(cert_expirationStatus OK).
  • HSTS가 max-age와 함께 설정되어 있습니다.
이상 징후
  • CRITICAL 또는 HIGH 항목이 하나라도 있습니다. 예: 구버전 프로토콜 허용, 만료된 인증서.
  • cert_chain_of_trust 실패로 중간 인증서가 빠졌습니다.
  • --fast로 생략한 암호군 검사 항목이 보고서에 '미점검'으로 남습니다.
오탐 주의
  • SNI를 지정하지 않으면 다른 가상호스트의 인증서를 보고 '이름 불일치'로 오탐이 납니다.
  • 로드밸런서 뒤에서는 노드마다 결과가 달라질 수 있습니다. 대표 노드·VIP를 구분해 기록합니다.
  • --fast 결과의 '없음'은 '안전'이 아니라 '검사 안 함'일 수 있습니다.
  • 사내 CA가 서명한 인증서는 신뢰 저장소에 없어 실패로 보입니다. 정책상 허용 여부를 따로 판단합니다.
조치
  • 구버전 프로토콜·취약 암호군을 서버 설정에서 끄고 TLS 1.2 이상만 허용합니다.
  • 인증서 만료·체인 누락은 자동 갱신·중간 인증서 포함으로 조치합니다.
  • HSTS는 단계적으로 적용하고 includeSubDomains의 영향을 먼저 확인합니다.
재점검
  • 같은 옵션으로 다시 돌려 id별 severity가 낮아졌는지 비교합니다.
  • --fast를 뺀 전체 점검으로 생략 항목까지 확인합니다.

샘플 증적 (마스킹)

jq로 id·severity·finding만 뽑은 표입니다. 구버전 프로토콜 허용이 가장 먼저 조치할 항목입니다.

확인 절차 (비실행)

아래 명령은 승인된 점검에서 이미 저장된 결과 JSON·로그를 읽기만 합니다. 대상을 향해 요청을 보내지 않습니다.

판별 결과 JSON 요약 로컬 파일 읽기 
jq -r '.probes[] | [.notation, .rule, .action, .status] | @tsv' fixture/results/input-validation.json

승인된 점검에서 남긴 결과 파일을 읽습니다. 표기별로 어떤 규칙에 걸렸고 어떤 상태로 끝났는지 한눈에 봅니다.

검증 없이 통과한 표기 찾기 로컬 파일 읽기 
jq -r '.probes[] | select(.action == "pass") | .notation' fixture/results/input-validation.json

pass는 코드 검증을 통과한 표기입니다. 한 건이라도 있으면 그 표기의 응답 본문을 먼저 엽니다.

WAF 차단 로그 확인 로컬 파일 읽기 
grep -nE 'rule=(941|942)[0-9]{3} action=(block|log)' /var/log/fixture/waf.log | tail -20

941xxx는 XSS, 942xxx는 SQL 삽입 규칙 계열입니다. log는 차단하지 않고 기록만 한 것입니다.

앱 거부 로그 대조 로컬 파일 읽기 
grep -niE 'input_validation|invalid_input' /var/log/fixture/app.log | tail -20

WAF만 막고 코드는 통과시키는 상태를 가릅니다. 앱 거부 기록이 없으면 코드 조치가 남아 있습니다.

코드 경로 정적 확인 로컬 파일 읽기 
grep -rnE 'PreparedStatement|bindParam|escapeHtml|autoescape' app/src | head -20

명령을 실행하지 않고 소스에서 바인딩·이스케이프 적용 지점만 찾습니다.

판정 기준 · 오탐 · 조치

정상 출력
  • 짝으로 남긴 두 응답(참 조건·거짓 조건)의 상태 코드와 길이가 같고, 본문에 표기 원문이 보이지 않습니다.
  • 태그 형태 표기가 엔티티로 인코딩되어 문자 그대로 출력되고, 속성이나 이벤트가 늘지 않습니다.
  • 수식 표기가 그대로 출력되고 계산 결과가 보이지 않습니다.
  • 차단 로그에 action=block과 규칙 번호가 남고, 애플리케이션 로그에는 요청이 도달하지 않습니다.
이상 징후
  • 참 조건에서만 응답 길이·행 수가 달라집니다(불리언 차이).
  • 응답 본문에 표기가 원문 그대로 들어 있고, 속성·이벤트가 새로 생겼습니다.
  • 계산 결과가 출력되거나 템플릿 구문 오류로 스택 트레이스가 노출됩니다.
  • DB 오류 문구·스택 트레이스가 사용자 응답에 그대로 나옵니다.
오탐 주의
  • 응답 코드 하나로 단정할 수 없습니다. 200이라도 이스케이프되어 있으면 정상입니다.
  • WAF가 403을 주면 '안전'이 아니라 '검사되지 않음'입니다. 차단 로그와 애플리케이션 로그를 대조합니다.
  • 응답 길이 차이는 광고·타임스탬프·난수 때문에도 생깁니다. 여러 번 반복해 편차를 확인합니다.
  • 지연 함수 계열은 네트워크 지연과 구분이 어려워 단독 근거로 쓰지 않습니다.
  • 다른 사용자의 저장 데이터가 섞여 보이면 내 테스트 데이터인지 먼저 확인합니다.
조치
  • SQL은 파라미터 바인딩(Prepared Statement)으로 분리하고, 정렬·컬럼명은 허용 목록으로 고정합니다.
  • 출력은 문맥별 이스케이프(HTML·속성·JS·URL)를 적용하고, 가능하면 템플릿 엔진의 자동 이스케이프를 켭니다.
  • SSTI는 사용자 입력을 템플릿 원본으로 컴파일하지 않고, 값으로만 전달합니다.
  • 오류 메시지는 일반 문구로 바꾸고 상세 내용은 서버 로그로만 남깁니다.
재점검
  • 조치 후 같은 표기로 다시 점검해 남긴 응답의 상태·길이·본문이 동일해졌는지 확인합니다.
  • 차단 로그가 '차단'에서 '통과 후 코드에서 거부'로 바뀌었는지, 애플리케이션 로그에 거부 기록이 남는지 봅니다.
  • 회귀 테스트에 같은 표기를 넣어 배포마다 자동 확인합니다.

모의 응답 대조

같은 표기에 대한 두 서버의 판정 (합성 예시)

왼쪽은 400 거부 또는 이스케이프 출력, 오른쪽은 오류 노출·원문 반사·식 평가입니다. 코드 하나가 아니라 본문과 오류 문구를 함께 봐야 판정할 수 있습니다. 입력 & 출력을 짝으로 비교합니다.

차단 로그 예시

action=block은 경계에서 막힌 것, app-gateway result=reject는 코드에서 거부한 것입니다. 둘을 구분해야 'WAF만 막고 코드는 취약'인 상태를 놓치지 않습니다.

판정 기준 · 오탐 · 조치

정상 출력
  • 루프백·메타데이터 대역 요청이 400·403으로 거부되고 Egress 로그에 DENY가 남습니다.
  • 리다이렉트가 내부 상대 경로로만 정규화됩니다.
  • 허용 목록이 호스트 전체 일치로 비교되어 접미사 우회가 통과하지 않습니다.
이상 징후
  • 응답 본문에 내부 페이지 HTML·메타데이터 항목이 포함됩니다.
  • Location 헤더가 허용 목록 밖 외부 도메인을 가리킵니다.
  • Egress 로그에 사설·링크로컬 대역으로 나간 ALLOW 기록이 있습니다.
  • 검사는 통과했는데 실제 요청 목적지가 다른 경우(파서 차이)가 있습니다.
오탐 주의
  • 프록시가 모든 외부 요청을 막고 있어 'SSRF 불가'로 보일 수 있습니다. 코드 검증 여부를 따로 봅니다.
  • 리다이렉트 응답이 캐시에서 와서 이전 결과가 보일 수 있습니다. 캐시 우회 헤더로 다시 확인합니다.
  • 허용 목록에 실제로 필요한 파트너 도메인이 있어 '외부로 나간다'고 오탐할 수 있습니다.
  • DNS가 내부 주소로 해석되는 정상 구성(사내 도메인)과 SSRF를 구분합니다.
조치
  • SSRF는 목적지 허용 목록 + 사설·링크로컬 대역 차단 + DNS 재해석 방지를 함께 적용합니다.
  • 리다이렉트는 목적지를 상대 경로로 정규화하고, 외부 이동이 필요하면 확인 화면을 둡니다.
  • Egress 프록시를 기본 거부로 두고 필요한 목적지만 허용합니다.
재점검
  • 조치 후 새로 저장된 Egress 로그에서 400·403과 DENY 사유가 유지되는지 확인합니다.
  • 리다이렉트 응답의 Location이 내부 경로로만 정규화되는지 다시 봅니다.
